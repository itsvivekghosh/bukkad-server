# SLO Burn Rate Alert Runbook

This runbook describes triage steps for SLO burn-rate alerts generated by the multi-window, multi-burn-rate alerting system per Google SRE workbook recommendations.

## Alert Summary

| Alert | SLO | Window | Burn Rate | Severity | Action |
|-------|-----|--------|-----------|----------|--------|
| `SLOLatencyBurnRate1hCritical` | Latency (99.5% < 500ms) | 1h | 14.4x | Critical (Page) | Immediate investigation |
| `SLOLatencyBurnRate6hCritical` | Latency (99.5% < 500ms) | 6h | 6x | Critical (Page) | Immediate investigation |
| `SLOLatencyBurnRate24hWarning` | Latency (99.5% < 500ms) | 24h | 3x | Warning (Ticket) | Schedule investigation |
| `SLOLatencyMultiWindowBurnRateWarning` | Latency (99.5% < 500ms) | 1h+6h | 6x + 3x | Warning (Ticket) | Schedule investigation |
| `SLOAvailabilityBurnRate1hCritical` | Availability (99.9% success) | 1h | 14.4x | Critical (Page) | Immediate investigation |
| `SLOAvailabilityBurnRate6hCritical` | Availability (99.9% success) | 6h | 6x | Critical (Page) | Immediate investigation |
| `SLOAvailabilityBurnRate24hWarning` | Availability (99.9% success) | 24h | 3x | Warning (Ticket) | Schedule investigation |
| `SLOAvailabilityMultiWindowBurnRateWarning` | Availability (99.9% success) | 1h+6h | 6x + 3x | Warning (Ticket) | Schedule investigation |

## Understanding Burn Rate

**Burn rate** measures how fast you're consuming your error budget relative to the SLO target:

- **Burn rate = 1**: Consuming budget at exactly the SLO rate (on track)
- **Burn rate > 1**: Consuming budget faster than allowed (budget will exhaust early)
- **Burn rate < 1**: Consuming budget slower than allowed (budget will last longer)

The alert thresholds correspond to:
- **14.4x over 1h**: ~2% of 30-day budget consumed in 1 hour (page immediately)
- **6x over 6h**: ~5% of 30-day budget consumed in 6 hours (page)
- **3x over 24h**: ~10% of 30-day budget consumed in 24 hours (ticket)
- **Multi-window (1h > 6x AND 6h > 3x)**: Sustained elevated burn rate (ticket)

## Triage Steps

### 1. Identify the Affected Service and Endpoint

```bash
# Check which service/endpoint is firing the alert
# The alert labels contain: service, method, uri, slo, window
kubectl get prometheusrules -n bhukkad -o yaml | grep -A 20 "SLOLatencyBurnRate\|SLOAvailabilityBurnRate"
```

In Grafana, check the **SLO / Error Budget** dashboard:
- "Error Budget Remaining" gauges show current budget status
- "Burn Rate" timeseries show which endpoints have elevated burn rates
- "30-Day Budget Projection" shows projected budget exhaustion

### 2. Determine SLO Type

**Latency SLO (99.5% < 500ms)** - `slo="latency"` label:
- High latency requests exceeding 500ms threshold
- Check: downstream dependencies, database queries, cache misses, thread pool saturation

**Availability SLO (99.9% success)** - `slo="availability"` label:
- 5xx errors exceeding 0.1% error budget
- Check: application exceptions, downstream service failures, timeouts, resource exhaustion

### 3. Investigate Latency SLO Alerts

#### Check Current Latency Distribution
```promql
# 5m latency distribution for the affected endpoint
histogram_quantile(0.99, sum(rate(bhukkad_http_requests_seconds_bucket{service="<service>", uri="<uri>"}[5m])) by (le))
histogram_quantile(0.95, sum(rate(bhukkad_http_requests_seconds_bucket{service="<service>", uri="<uri>"}[5m])) by (le))
histogram_quantile(0.50, sum(rate(bhukkad_http_requests_seconds_bucket{service="<service>", uri="<uri>"}[5m])) by (le))
```

#### Common Latency Causes
| Cause | Symptoms | Investigation |
|-------|----------|---------------|
| Database slow queries | High p99, normal p50 | Check `pg_stat_statements`, look for missing indexes |
| Cache misses | Latency spikes under load | Check Redis hit rate, cache warming |
| Downstream service latency | Correlated with upstream calls | Check circuit breaker status, downstream SLOs |
| Thread pool exhaustion | Queue buildup, increased latency | Check executor metrics, thread pool sizing |
| GC pressure | Periodic latency spikes | Check JVM GC metrics, heap usage |
| Network issues | Intermittent high latency | Check network policies, service mesh |

#### Quick Mitigations
- Enable request hedging for idempotent endpoints
- Increase timeout budgets temporarily
- Scale out the affected service
- Fail fast with circuit breakers for degraded dependencies

### 4. Investigate Availability SLO Alerts

#### Check Error Rate
```promql
# 5m error rate by status code
sum(rate(bhukkad_http_requests_seconds_count{service="<service>", status=~"5.."}[5m])) by (status)
/ sum(rate(bhukkad_http_requests_seconds_count{service="<service>"}[5m]))
```

#### Check Application Logs
```bash
# Check for exception patterns in the last 15 minutes
kubectl logs -n bhukkad -l app=bhukkad,service=<service> --since=15m | grep -E "ERROR|Exception|5xx" | head -50
```

#### Common Availability Causes
| Cause | Symptoms | Investigation |
|-------|----------|---------------|
| Downstream service down | 502/503/504 errors | Check downstream service health, circuit breakers |
| Database connection pool exhaustion | 500 errors, timeouts | Check HikariCP metrics, connection leaks |
| Resource exhaustion (OOM, CPU) | Pod restarts, 500 errors | Check pod resources, OOM kills |
| Bad deploy / config change | Sudden error spike | Check recent deployments, rollback if needed |
| Dependency cascade failure | Correlated errors across services | Check service dependency graph |

#### Quick Mitigations
- Rollback recent deployment if correlated
- Increase circuit breaker timeout thresholds temporarily
- Add capacity (HPA, manual scaling)
- Enable graceful degradation (fallback responses)

### 5. Check Related Metrics

#### Service Health
```promql
# Overall service health
up{service="<service>"}
```

#### Resource Utilization
```promql
# CPU and memory
sum(rate(container_cpu_usage_seconds_total{namespace="bhukkad", pod=~"<service>.*"}[5m])) by (pod)
container_memory_working_set_bytes{namespace="bhukkad", pod=~"<service>.*"}
```

#### Database
```promql
# Connection pool
hikaricp_connections_active{pod=~"<service>.*"} / hikaricp_connections_max{pod=~"<service>.*"}
```

#### Cache
```promql
# Redis hit rate
rate(redis_keyspace_hits_total[5m]) / (rate(redis_keyspace_hits_total[5m]) + rate(redis_keyspace_misses_total[5m]))
```

### 6. Escalation and Communication

**Critical (Page) Alerts:**
1. Acknowledge within 5 minutes
2. Begin investigation immediately
3. Update incident channel with findings every 15 minutes
4. Escalate to team lead if no progress in 30 minutes
5. Consider engaging on-call for dependent services

**Warning (Ticket) Alerts:**
1. Create ticket in tracking system
2. Assign to service owner
3. Target investigation within 4 hours
4. Target resolution within 24 hours

### 7. Post-Incident Actions

After resolution:
1. Document root cause in incident retrospective
2. Update runbook if new failure mode discovered
3. Consider adjusting SLO targets or alert thresholds if inappropriate
4. Add preventive measures (tests, monitoring, capacity)

## Useful Queries Reference

### Current Error Budget Consumption (1h window)
```promql
# Latency
1 - sum(rate(bhukkad_http_requests_seconds_bucket{le="0.5"}[1h])) by (service, method, uri)
  / sum(rate(bhukkad_http_requests_seconds_count[1h])) by (service, method, uri)

# Availability
sum(rate(bhukkad_http_errors_total[1h])) by (service, method, uri)
  / sum(rate(bhukkad_http_requests_seconds_count[1h])) by (service, method, uri)
```
